# Vertix Commerce local QA — 9 October 2026

> Historical report before the authorized implementation follow-up. See [the completion check](completion-check-2026-10-09.md) for resolved code gaps, current tests and remaining external launch prerequisites.

Result: the current UI and core inquiry workflow work, but the complete requested product is not production-ready. Tests ran against localhost in connected Chrome, not a deployed production environment. This was a test/report task; application behavior and business configuration were not changed.

## Passed

- Chrome desktop: styled homepage, generic expertise heading, visible eBay and Walmart service links, contact, privacy, terms, booking fallback, and FAQ expansion. Both visible service pages load without a 404. No deleted services were restored.
- Chrome responsive previews: public homepage at 320, 390, and 768 pixels; mobile navigation expansion and service navigation; admin overview and drawer at 390 pixels. Normal viewport sizes were restored afterward.
- Admin: all eight collection lists and both globals open in Chrome. Overview navigation, collapsible groups, active section, mobile drawer, service editor tabs, menu visibility controls, search, and filter panel work. No existing business record was edited through the browser.
- Inquiry: empty submission and missing consent blocked by browser validation. A fictional consented inquiry was accepted, visible in admin, stored with consent timestamp and future retention expiry, and inaccessible anonymously. Notification status correctly showed email not configured. The identified test inquiry was removed; no existing customer records were deleted and no notification email was sent.
- Assistant: English and German fallback responses; German password refusal; explicit offline human-follow-up notice; contact and booking-fallback links. These were fallback/safety tests, not successful live model answers.
- `npm run test`: 46 tests pass, including 10 new mocked API failure tests (provider failure, missing provider configuration, empty answers, unavailable knowledge, oversized history, rate limits, storage failure, missing consent, and unavailable storage).
- `npm run test:admin`: 28 checks pass, including owner login, admin rendering/styles, draft saves, publish/rename/hide/disable round trips using disposable fixtures, anonymous protection, and viewer restrictions.
- `npm run test:public`: 16 checks passed in this run, including optional verification/cleanup of the browser-created QA inquiry. A normal run without that fixture performs 14 checks with the current two public services. Invalid JSON/input return 400; isolated local test buckets return 429 at their limits; unknown service returns 404.
- TypeScript and production build pass. A passing build or smoke suite does not establish that every original feature is implemented.

## Issues and gaps

1. **Assistant is not live locally.** No OpenAI key is configured and the dashboard shows zero approved articles. Service questions safely fall back rather than receiving substantive answers. Actual provider connectivity was not tested; provider failure behavior was tested with mocks.
2. **Assistant admin settings are not wired into runtime.** Code inspection: the chat route and dock do not read the assistant global. Enable/disable, additional instructions, lead-capture preference, and custom offline message therefore do not currently control the agent. Chat messages are held in browser component state; the route does not create conversation records. Direct chat lead capture and live human messaging are not implemented.
3. **Some CMS content does not reach public screens.** Browser: the contact select still offers all 13 starter services although only two remain in the CMS. Code inspection: it imports the static catalogue. Detailed service content, benefits, and process steps are editable in admin but omitted by the public service mapper/page, which renders a generic scope paragraph. Homepage FAQs and countries are also hardcoded rather than loaded from their editors.
4. **Contact integrations are incomplete.** Email provider, public floating email, and booking environment configuration are absent locally. Booking links go to `/contact?intent=meeting`; that screen is the ordinary inquiry form, not an actual booking system. Code inspection: CMS contact/booking values are not consumed by the dock/homepage. Email notifications and real password-reset email delivery were not tested. The floating email button is absent, so email/chat overlap with a configured button remains unverified.
5. **Mobile chat needs correction.** Its launcher has no accessible name below the `sm` breakpoint because its only text label is hidden. At 320/390-pixel Chrome previews with a scrollbar, the panel's left edge measured -7 pixels, clipping the left side. Desktop chat rendered correctly. German response text works, but headings, labels, the greeting, and error text remain English.
6. **Footer social data needs review.** The single visible Facebook-style link has the label `Faceb` and points to a Variosoft service page, not a business social profile. Its saved value was not changed during testing.
7. **Production privacy/security work remains.** Privacy and terms visibly describe themselves as drafts/placeholders. Expiry metadata does not perform automatic retention deletion. The current limiter is process-local, has no bucket cleanup, and keys directly from the supplied forwarded-IP header; the tests prove single-process throttling, not production distributed abuse protection. No deployment/security audit was performed.
8. **Contact failure UX needs follow-up.** Code inspection: form submission has no network exception handler, in-flight submit guard, or reset after success. Browser network loss was not injected, so that failure path remains unverified. The consent text references the privacy notice without an adjacent link.

A Payload import-map warning appeared in the initial browser console, but no admin screen failed. Relationship category cells temporarily showed a placeholder before loading their correct labels. Neither was treated as a reproducible blocking navigation failure.

## Evidence and reruns

![Verified desktop admin dashboard](../artifacts/qa-2026-10-09/admin-desktop.jpg)

Run `npm run test`, `npm run typecheck`, and `npm run build`. With a local server running, use `npm run test:admin` and `npm run test:public`. The scripts reject non-localhost destinations. Credentials/cookies are not printed. Public rate-limit checks use isolated fictional forwarded-IP keys so they do not consume the normal browser client's request budget.

The optional `PUBLIC_QA_LEAD_ID` cleanup is only for a just-created browser QA record whose exact fictional name and email match the script. Do not set it for real customer data. Real email delivery, booking completion, production TLS/storage/backups, real mobile keyboards, password-reset completion, all-role browser sessions, and live escalation require separate verification.
